# ㄅㄆㄇ猜歌 — Guess the lyrics by initial consonant

只給每個字的**注音聲母**，猜出這是哪首歌、哪句歌詞。

```
ㄊ  ㄑ  ㄙ  ㄉ  ㄧ  ㄩ     →  天青色等煙雨
```

純 HTML / CSS / JS，沒有 build step。用瀏覽器直接打開 `index.html` 就能玩。

---

## 快速開始

```bash
npm install          # 兩個開發用套件（pinyin-pro、opencc-js），網站本身不依賴它們
npm run dev          # http://localhost:5173
npm test             # 跑檢查 + 房間狀態機 + 整局流程煙霧測試
npm run check:room   # 只跑即時競賽的房間邏輯
```

想直接玩也可以：**雙擊 `index.html`**。題庫是用一般 `<script>` 掛上去的，
所以 `file://` 也能跑，不一定要開伺服器。

## 新增歌曲

只要改 `data/songs.source.json`，注音聲母會自動算出來。檔案是**依年份由舊到新排序**的，
`year` 請務必填，年代分組要靠它：

```json
{
  "id": "jay-qingtian",
  "title": "晴天",
  "artist": "周杰倫",
  "year": 2003,
  "aliases": ["晴天 (Sunny Day)"],
  "lines": ["故事的小黃花", "從那年蟬鳴的夏天"]
}
```

然後跑：

```bash
npm run build:questions
```

一首歌的每一句會產生兩題：**看歌詞猜歌名**、**給歌名猜歌詞**。

### 一首歌請多放幾句

同一首歌只放一句的話，那句被記住之後這首歌就沒戲唱了；而且如果那句剛好是副歌，
猜歌名會太好猜。多放幾句不同段落的歌詞，同一首歌就有好幾種問法。目前平均每首 4.2 句。

### 檢查多音字

```bash
npm run audit          # 列出所有「換個讀音就會換成別的聲母」的字
npm run audit -- --all # 連只有一種聲母的多音字也列出來
```

程式沒辦法自己判斷哪個讀音才對，但可以把有可能選錯的位置全找出來。
照著唸一次，跟顯示的聲母不一樣就用 `initials` 手動指定。

`npm run build:questions` 跑完會列出**歌詞裡直接出現歌名**的句子——那種題目猜歌名
等於送分，看到清單很長就表示該幫那幾首補幾句別段的歌詞了。

### 想不起旋律？點歌名去聽

猜歌詞的題目會把歌名做成 YouTube 連結（開新分頁）。歌名本來就寫在題目上，
所以不會洩漏答案——要猜的是歌詞。

預設連到「歌手＋歌名」的搜尋結果，這樣 192 首歌都不用另外維護。想指定某一支
影片的話，在來源檔加上 `youtube` 欄位（填影片 id，不是整串網址）：

```json
{
  "id": "eason-taotai",
  "title": "淘汰",
  "artist": "陳奕迅",
  "year": 2007,
  "youtube": "影片 id",
  "lines": ["我說了所有的謊"]
}
```

猜歌名的題目**不會**放連結，那等於直接把答案送出去。

### 多音字怎麼辦

自動轉換用的是 pinyin-pro。它的**詞庫是簡體的**，直接餵繁體進去它認不出詞，
只能一個字一個字猜讀音，多音字就會挑錯：長大→cháng、音樂→lè、彈奏→dàn、
馬車→jū、曬乾→qián。所以 `build-questions.mjs` 查讀音前會先用 opencc-js
把歌詞轉成簡體，算完再把注音貼回原本的繁體字（轉換是逐字的，字數不會變）。

這樣還是會有漏網之魚，遇到時手動指定該句的聲母：

```json
"lines": [
  { "text": "重來一次", "initials": "ㄔ ㄌ ㄧ ㄘ" }
]
```

`npm run build:questions` 會檢查你給的聲母數量跟中文字數對不對得上，不對會警告。
`initials` 只對應**中文字**，句子裡的空白與標點還是照歌詞原樣排版，所以覆寫不會把版面弄亂。

目前只剩一句需要手動指定：〈消愁〉的「一杯敬**朝**陽」（會被讀成 cháo）。

### 聲母規則

有聲母的字取聲母；零聲母的字取注音的**第一個符號**（跟大家寫注音文的習慣一樣）：

| 字 | 注音 | 顯示 |
|---|---|---|
| 說 | ㄕㄨㄛ | ㄕ |
| 我 | ㄨㄛˇ | ㄨ |
| 愛 | ㄞˋ | ㄞ |
| 月 | ㄩㄝˋ | ㄩ |
| 兒 | ㄦˊ | ㄦ |

## 多人競賽

兩種玩法：**即時搶答**要部署 Worker，**出考卷**不用後端。

### 即時搶答（主持人開房，最快答對的拿分）

```
主持人  開一間房 → 拿到房號 7K2P → 等人進來 → 按開始
挑戰者  輸入房號進房 → 名字出現在名單上 → 等主持人開始
每一題  大家同時看到同一題 → 誰先答對誰拿分 → 公布答案 → 下一題
```

- **只有第一個答對的人拿分**，答越快分數越高（基本 100 ＋ 最多 60 的速度分）。
- 答錯不扣分，也不會被鎖住，可以一直猜到有人搶到或時間到。
- **錯字容忍照舊**：六個字以上差一個字仍算對，但分數打八折。
- 判定由**伺服器**做。搶答期間答案根本不會傳到瀏覽器，所以開 devtools 也看不到——
  這順便解決了單人模式那個「答案都在前端」的問題。

#### 要先部署

即時搶答需要有人排先後順序，這件事只有伺服器做得到，所以多了一支 Worker
（`worker/`）跟一個 Durable Object（一間房一個實例，用房號當 id）。

```bash
npx wrangler deploy
```

沒部署、或直接用 `file://` 打開的話，這個分頁會連不上——下面那個玩法不用伺服器。
Durable Objects 需要 Workers 付費方案；只想玩下面那種就不用管。

### 出考卷（不用後端）

**同一組代碼＝同一份考卷**，各玩各的再比分數。

```
主持人  選好題型/年代/難度/題數 → 建立比賽 → 拿到 4 碼代碼 7K2P
          ↓ 把代碼或邀請連結傳出去
挑戰者  貼上代碼 → 抽到完全一樣的題目、順序、開場送字
          ↓ 玩完各自拿到一段成績碼
主持人  把大家的成績碼貼進排行榜 → 分出高下
```

### 代碼為什麼只有 4 個字

4 個字剛好 20 個位元：設定佔 10 位（題型 2、難度 2、年代 4、題數 2），
種子佔 10 位，也就是同一組設定下有 1024 份不同的考卷。用的字母表刻意拿掉
**I L O U**——I 跟 1、L 跟 1、O 跟 0 不管用唸的還用看的都會搞混。
真的抄錯了也沒關係，輸入時會自動把 I/L 當 1、O 當 0、U 當 V 救回來。

題數因此只能是 **5 / 10 / 20 / 40**（2 個位元放得下的四個選項）。

### 為什麼題目會一樣

代碼裡包了一個亂數種子跟全部設定（題型、年代、難度、題數）。抽題用的不是
`Math.random()`，而是由種子推出來的 mulberry32，所以同一組代碼推出來的順序永遠一樣。

每一題的「開場送字」另外用 `種子＋題號` 推一條獨立的亂數，這樣**有人買提示也不會
害後面的題目跟別人不同步**——如果共用同一條亂數流，多消耗幾個亂數就整份考卷歪掉了。

### 跟單人模式的差別

| | 無盡挑戰 | 多人競賽 |
|---|---|---|
| 結束條件 | 三顆愛心用完 | 固定題數（5～40） |
| 答錯 | 扣愛心 | 只歸零連擊，繼續下一題 |
| 最高分紀錄 | 會寫入 | 不寫入（題數不同不能比） |

### 幾個老實話

- 排行榜存在**你自己的瀏覽器**（localStorage），不是伺服器。換裝置就看不到了。
- 成績碼只是方便貼來貼去，**不防作弊**——想改分數的人改得掉。朋友間玩夠用。
- 題庫連答案都在前端，開 devtools 就看得到。要辦真的有獎競賽，答案得放伺服器端，
  也就是下面說的 Supabase 那條路。

## 遊戲設計

| 機制 | 說明 |
|---|---|
| 無盡挑戰 | 一題接一題，三顆愛心用完結束 |
| 多人競賽 | 主持人建代碼，大家玩同一份考卷再比分數，詳見上面 |
| 年代 | **可複選**：90年代以前 / 2000 / 2010 / 2020 年代，勾幾個就玩幾個年代的聯集。按鈕上標出該年代有幾首歌，沒歌的年代自動停用；「題庫」那格會跟著勾選即時顯示目前選到幾首幾題 |
| 開場送字 | 每題先直接送出一部分中文字（虛線格），其餘才是要猜的聲母；至少留兩個字要猜 |
| 猜歌名時 | 固定送出那句歌詞的開頭兩個字，讓你有線索起頭 |
| 連擊倍率 | 每答對一題 +0.15 倍，最高 ×3 |
| 時間獎勵 | 剩餘每秒 +4 分 |
| 難度 | 同時決定秒數與送字比例：悠閒 60 秒送 45% / 正常 30 秒送 30% / 刺激 15 秒送 12% |
| 提示 | 每次扣 50 分：報歌手 → 揭字數/首字 → 再揭一個字（不會重複揭已經送過的字） |
| 對答案 | 送出後如果沒有完全答對，會把「你打的」跟「正解」並排，逐字標出差在哪：你多打的字劃掉，正解裡你漏掉的字底線標起來。比對前會先去掉標點與空白，所以那些不算錯 |
| 跳過 | 每局三次，連擊歸零但不扣愛心 |
| 錯字容忍 | 六字以上的答案，差一個字仍算對 |
| 同音字容忍 | 他／她／牠、你／妳、的／得／地、在／再、那／哪、做／作、啊／阿／呀、裡／裏、台／臺、著／着…唸起來一樣就算對。你是聽歌回想歌詞，不是在默寫，選錯字不該被判死；反正同音字的注音聲母也一樣，題目不會因此變簡單 |

輸入框有處理**注音輸入法選字中的 Enter**（`compositionstart` / `compositionend`），
選字時按 Enter 不會誤送出。

## 題庫要用什麼存？我的建議

短答：**現在這樣（JSON）就夠了，等你真的需要下面任何一項再上 Supabase。**

### 為什麼先用 JSON

- 題庫是**唯讀**的，全部才幾十 KB，跟著網站一起下載反而比打 API 快。
- 沒有後端、沒有 API key、沒有 CORS、沒有網路失敗要處理。
- 部署到 GitHub Pages / Netlify / Vercel 直接免費靜態託管。
- 改歌詞就是改一個 JSON 檔，用 git 管版本，改壞了 `git revert` 就好。

一兩百首歌都還在這個方案的舒適圈內。

### 什麼時候該換 Supabase

出現下面任何一項，就值得換：

1. **排行榜 / 分數紀錄** — 需要寫入，靜態檔做不到。
2. **每日一題** — 全站同一題、有人算得出來要防作弊，題目答案就不該全部塞在前端。
3. **想在網頁上新增歌曲**，不想每次都改檔案 + 重新部署。
4. **多人一起維護題庫**，需要權限控管。
5. 題庫大到**幾千題**，希望依難度／年代分頁載入。

> 注意第 2 點：現在整份題庫（含答案）都在前端，打開 devtools 就看得到答案。
> 純娛樂沒差，但要做競賽型的每日挑戰就得把答案留在伺服器端。

### 要換的話怎麼換

已經幫你準備好了，三步：

```bash
# 1. 在 Supabase SQL Editor 貼上並執行
cat supabase/schema.sql

# 2. 產生 seed SQL，一樣貼進 SQL Editor 執行
npm run export:supabase > supabase/seed.sql
```

3. 打開 `assets/data.js`，把 `loadQuestions()` 換成檔案底部註解裡的 Supabase 版本，
   並在 `index.html` 加上 supabase-js 的 CDN script。**遊戲程式完全不用動。**

資料表設計：`songs`（歌曲）+ `lyric_lines`（歌詞句，含預先算好的 `tiles`）。
把聲母存進資料庫而不是前端即時算，是為了不用在瀏覽器載一份幾百 KB 的漢字拼音表。

RLS 已經設成**匿名只能讀不能寫**，所以 anon key 放在前端是安全的。
